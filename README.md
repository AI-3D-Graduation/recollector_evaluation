## 개요

3D 모델의 품질을 비교할 때는 **시각적 퀄리티**와 **성능 효율성** 사이의 균형을 평가해야 합니다. 이 가이드는 두 GLB/glTF 모델을 객관적으로 비교하는 데 필요한 핵심 지표들을 제공합니다.

---

## 핵심 비교 지표

### 1️⃣ 기하학적 복잡도 (Geometry Complexity)

#### 삼각형 수 (Triangle Count)
- **의미**: 3D 모델의 폴리곤 복잡도
- **영향**: 
  - ↑ 많을수록: 더 디테일하고 부드러운 표면
  - ↓ 적을수록: 렌더링 성능 향상, GPU 부담 감소
- **비교 기준**:
  - 비슷한 디테일에서 삼각형 수가 적은 쪽이 우수
  - 모바일: ~10만개 이하
  - PC/웹: ~100만개 이하
  - VR: ~5만개 이하 (양안 렌더링)

#### 정점 수 (Vertex Count)
- **의미**: 3D 공간상의 점(point) 개수
- **영향**: 
  - GPU 메모리 사용량
  - 버텍스 셰이더 처리 부하
- **비교 기준**:
  - 정점 당 더 많은 디테일을 표현하면 효율적

#### Vertices/Triangles 비율
- **의미**: 인덱싱 효율성 지표
- **최적 범위**: **0.5 ~ 1.5**
- **평가**:
  - 비율이 1.0에 가까우면 인덱스 버퍼를 효율적으로 사용
  - 3.0 이상이면 중복 정점이 많아 비효율적
  - 0.3 이하면 정점이 과도하게 공유되어 UV/Normal이 왜곡될 수 있음

#### 프리미티브 수 (Primitive Count)
- **의미**: 렌더링 단위 (각 Primitive = 1 Draw Call)
- **영향**: CPU 오버헤드
- **비교 기준**:
  - 적을수록 좋음 (배칭/머징 최적화)
  - 200개 이상이면 문제 가능성

---

### 2️⃣ 텍스처 퀄리티

#### 텍스처 해상도
- **주요 크기**:
  - 512×512 (0.5K): 저품질, 모바일 최적화
  - 1024×1024 (1K): 일반 품질
  - 2048×2048 (2K): 고품질, 웹/모바일 권장
  - 4096×4096 (4K): 매우 고품질, PC 전용
  - 8192×8192 (8K): 초고품질, 고사양 PC 전용

- **메모리 계산**:
  - RGBA PNG (비압축): width × height × 4 bytes
  - 예: 2K 텍스처 = 2048 × 2048 × 4 = 16MB
  - 예: 4K 텍스처 = 4096 × 4096 × 4 = 64MB

- **비교 기준**:
  - 같은 시각적 품질이라면 작은 텍스처가 우수
  - 여러 작은 텍스처보다 하나의 큰 아틀라스가 효율적 (Draw Call 감소)

#### 텍스처 개수
- **영향**: 
  - 메모리 사용량
  - 텍스처 바인딩 오버헤드
- **비교 기준**:
  - 적을수록 좋음 (단, 중복 제거 및 아틀라싱 필요)

#### 총 텍스처 픽셀 (Total Texture Pixels)
- **의미**: 모든 텍스처의 픽셀 수 합계
- **계산**: Σ(width × height)
- **비교 기준**: 실제 메모리 사용량을 나타내는 좋은 지표

#### 텍스처 포맷
- **PNG**: 무손실, 투명도 지원, 파일 크기 큼
- **JPEG**: 손실 압축, 파일 크기 작음, 투명도 없음
- **WebP**: 효율적 압축, 브라우저 지원 필요
- **KTX2/Basis Universal**: GPU 압축, 최고 효율성

---

### 3️⃣ 머티리얼 복잡도

#### PBR (Physically Based Rendering) 텍스처
- **Base Color**: 기본 색상 (필수)
- **Metallic/Roughness**: 금속성/거칠기 (PBR 핵심)
- **Normal Map**: 표면 디테일 증가 (추천)
- **Occlusion Map**: 주변광 차폐 (현실감↑)
- **Emissive Map**: 발광 효과 (선택)

#### 비교 기준
- **Normal Map 유무**: 
  - ✅ 있음: 적은 폴리곤으로도 디테일 표현 가능
  - ❌ 없음: 폴리곤으로만 디테일 표현
  
- **Occlusion Map 유무**:
  - ✅ 있음: 틈새/구석의 그림자가 현실적
  - ❌ 없음: 밋밋한 느낌

- **텍스처 수 vs 품질**:
  - 많은 텍스처 = 높은 품질 + 높은 메모리
  - 적절한 균형 필요

#### Metallic/Roughness 값
- **Metallic Factor**:
  - 0.0: 비금속 (나무, 플라스틱, 천)
  - 1.0: 금속 (철, 금, 은)
  
- **Roughness Factor**:
  - 0.0: 매끄러움 (거울, 광택)
  - 1.0: 거칠음 (돌, 천, 고무)

---

### 4️⃣ 파일 효율성

#### 파일 크기
- **영향**:
  - 네트워크 다운로드 시간
  - 로딩 속도
  - 저장 공간
  
- **비교 기준**:
  - 파일 크기 / 삼각형 수 비율
  - 예: 100KB당 1만 삼각형이면 효율적

#### 압축 기술
- **Draco 압축** (KHR_draco_mesh_compression):
  - ✅ 장점: 기하학 데이터 50~90% 압축
  - ❌ 단점: 디코딩 시간 추가
  - **권장**: 웹/모바일에서 필수

- **KTX2/Basis 텍스처 압축**:
  - GPU에서 직접 디코딩
  - 메모리 및 파일 크기 대폭 감소

---

### 5️⃣ 최적화 수준

#### 드로우 콜 (Draw Calls)
- **의미**: GPU에게 그리기 명령을 내리는 횟수
- **영향**: CPU 병목 현상의 주요 원인
- **권장 기준**:
  - 모바일: 50개 이하
  - PC: 200개 이하
  - VR: 100개 이하

- **최적화 방법**:
  - 메시 병합 (Mesh Merging)
  - 텍스처 아틀라스 (Texture Atlas)
  - 인스턴싱 (Instancing)

#### Vertex Attributes
- **필수**:
  - `POSITION`: 정점 위치 (필수)
  
- **권장**:
  - `NORMAL`: 조명 계산에 필수
  - `TEXCOORD_0`: 텍스처 매핑 (UV 좌표)
  
- **선택**:
  - `TANGENT`: Normal Map 사용 시 필요
  - `COLOR_0`: 버텍스 컬러
  - `JOINTS_0`, `WEIGHTS_0`: 스켈레탈 애니메이션

#### 인덱싱 사용
- **Indexed Geometry**: 
  - ✅ 정점 재사용으로 메모리 효율↑
  - indices 있으면 보통 30~50% 메모리 절약
  
- **Non-Indexed**:
  - ❌ 정점 중복으로 메모리 낭비

---

### 6️⃣ 구조 복잡도

#### 메시 개수 (Mesh Count)
- **영향**:
  - 관리 및 편집 용이성
  - 씬 그래프 복잡도
  
- **비교 기준**:
  - 논리적 구분에 필요한 만큼만 분리
  - 과도한 분리는 드로우 콜 증가

#### 노드 계층 깊이
- **영향**:
  - Transform 계산 오버헤드
  - 애니메이션 복잡도
  
- **권장**:
  - 깊이 10 이하
  - 불필요한 중첩 제거

## 최적화 팁

### 🔧 기하학 최적화
1. **Decimation (폴리곤 감소)**
   - Blender: Decimate Modifier
   - Maya: Mesh > Reduce
   - 목표: 시각적 품질 유지하며 50% 감소

2. **리토폴로지 (Retopology)**
   - 고해상도 스캔/스컬프팅 → 저해상도 메시로 재구성
   - Normal Map으로 디테일 보존

3. **LOD (Level of Detail)**
   - 거리에 따라 다른 해상도 모델 사용
   - 예: LOD0 (10만 tri) → LOD1 (5만) → LOD2 (1만)

### 🖼️ 텍스처 최적화
1. **텍스처 아틀라스**
   - 여러 텍스처를 하나의 큰 텍스처로 결합
   - 드로우 콜 대폭 감소

2. **해상도 조정**
   - 중요 부분: 고해상도 유지
   - 보이지 않는 부분: 저해상도
   - 배경/멀리 있는 오브젝트: 저해상도

3. **압축 포맷 사용**
   - Basis Universal (KTX2)
   - WebP
   - JPEG for base color (투명도 불필요 시)

4. **Mipmap 생성**
   - 거리에 따라 자동으로 낮은 해상도 사용
   - 메모리 및 렌더링 성능 향상

### 🎨 머티리얼 최적화
1. **텍스처 채널 패킹**
   - Metallic + Roughness를 한 텍스처에 (R=Metallic, G=Roughness)
   - Occlusion + 다른 데이터 결합

2. **불필요한 맵 제거**
   - Emissive가 필요 없으면 제거
   - 평평한 표면은 Normal Map 불필요

3. **머티리얼 공유**
   - 비슷한 재질은 하나의 머티리얼로 통합
   - 텍스처 아틀라스와 결합

### 📦 파일 최적화
1. **Draco 압축 활성화**
   ```bash
   # glTF-Transform 사용
   gltf-transform draco input.glb output.glb
   ```

2. **텍스처 압축**
   ```bash
   # Basis 압축
   gltf-transform etc1s input.glb output.glb
   ```

3. **불필요한 데이터 제거**
   - 사용하지 않는 애니메이션
   - 빈 노드
   - 중복 정점 병합

## 품질 평가 체크리스트

### ✅ 기본 품질 (필수)
- [ ] 정점/삼각형 비율이 0.5~1.5 범위
- [ ] 모든 메시에 NORMAL 속성 존재
- [ ] 텍스처가 있다면 TEXCOORD_0 존재
- [ ] 인덱스 버퍼 사용 중
- [ ] 파일 크기가 타겟 플랫폼 기준 이내

### ⭐ 고품질 (권장)
- [ ] Normal Map 사용으로 표면 디테일 증가
- [ ] Occlusion Map으로 현실감 향상
- [ ] PBR 머티리얼 제대로 설정 (Metallic/Roughness)
- [ ] 텍스처 해상도가 적절 (2K 권장)
- [ ] 드로우 콜이 플랫폼 권장치 이내

### 🏆 최적화 완료 (우수)
- [ ] Draco 압축 적용
- [ ] 텍스처 아틀라스 사용
- [ ] LOD 레벨 구현
- [ ] 텍스처 압축 포맷 사용 (KTX2)
- [ ] 불필요한 정점/폴리곤 제거 완료
- [ ] 메시 병합으로 드로우 콜 최소화

## 비교 시나리오 예시

### 시나리오 1: 캐릭터 모델
**모델 A**
- 삼각형: 50,000
- 텍스처: 2K × 5개 (Base, Normal, Metallic/Roughness, Occlusion, Emissive)
- 파일 크기: 8MB
- Normal Map: ✅
- Draco: ✅

**모델 B**
- 삼각형: 150,000
- 텍스처: 4K × 3개 (Base, Normal, Metallic/Roughness)
- 파일 크기: 25MB
- Normal Map: ✅
- Draco: ❌

**평가**:
- **디테일**: B가 더 높은 폴리곤 수로 우수
- **텍스처**: B가 더 높은 해상도 (4K vs 2K)
- **효율성**: A가 Draco 압축으로 파일 크기 1/3
- **최적화**: A가 모바일/웹에 적합, B는 PC 전용
- **결론**: 타겟이 모바일/웹이면 A, 고사양 PC면 B

### 시나리오 2: 건축물 모델
**모델 A**
- 삼각형: 200,000
- 드로우 콜: 15개
- 텍스처: 1K × 8개
- 텍스처 아틀라스: ✅

**모델 B**
- 삼각형: 180,000
- 드로우 콜: 120개
- 텍스처: 2K × 50개
- 텍스처 아틀라스: ❌

**평가**:
- **폴리곤**: 비슷함
- **드로우 콜**: A가 압도적으로 우수 (15 vs 120)
- **텍스처**: B가 고품질이지만 관리 어려움
- **성능**: A가 CPU 효율성 훨씬 우수
- **결론**: A가 훨씬 최적화됨

### 3D 모델링 및 최적화

- **Basis Universal**: 텍스처 압축
- **ImageMagick**: 일괄 리사이징
